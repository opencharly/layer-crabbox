# 2026.296.1129 — fix(crabbox): make the root candy resolvable from a remote ref

## Summary

Fixes a regression introduced by #16, found by the FIRST consumer to bump to its
tag: a remote `@github.com/opencharly/layer-crabbox:<tag>` ref could not resolve
the root candy.

**Mechanism (measured).** Adding a `candy/` directory to this repo changes how a
remote ref is scanned: `sdk/loaderkit/scan_candy.go` treats a repo WITH `candy/`
as a PROJECT and keys every candy as `repo/candy/<name>` (`scanRepoCandyDir`);
the root manifest is then not a candy at all. The resolver seeks the candy named
after the ref's leaf (`layer-crabbox`), finds none, and every consumer fails:

```
remote candy "@github.com/opencharly/layer-crabbox:v2026.296.1108" not found
  (candy "layer-crabbox" doesn't exist in github.com/opencharly/layer-crabbox)
```

Proven by the control: the same plugin project validates `OK` against the previous
release tag (`v2026.293.1705`, no `candy/`) and fails against `v2026.296.1108`.

**Fix.**

- The root candy is named after the repo (`crabbox` → `layer-crabbox`), which is
  what the root-level scan looks for (`name = path.Base(repoPath)`).
- The config candy moves OUT of `candy/` into its own named directory,
  `crabbox-containerd-config/`, and is referenced by path
  (`@.../layer-crabbox/crabbox-containerd-config:<tag>`). With NO `candy/`
  directory at the root, the repo is a root-level standalone candy again and the
  root manifest is scanned as the candy `layer-crabbox`.
- `discover:` lists `crabbox-containerd-config/` and `box/` (the root manifest is
  the project's own, no `path: "."` needed).
- Local references (`box/check-crabbox-cli`), the config candy's `require:` edge
  and the skill `owner:` follow the rename; README/SKILL/AGENTS paths follow the
  move.

**Migration.** `v2026.296.1108` is the only affected tag and no consumer is on it
(the `plugin-crabbox` pin bump was held when the failure surfaced). Consumers on
`v2026.293.1705` and earlier are unaffected. After this merges and tags,
`plugin-crabbox` pins the new tag in its own PR.

Refs opencharly/plugin-crabbox#15.

## Rulebook compliance

- **R0** — `/charly-internals:git-workflow`, `/charly-image:layer`,
  `/charly-check:check` loaded by path first.
- **R1** — the regression is RCA'd (below) and fixed in the same repo; no consumer
  is left on the broken tag.
- **R2** — one root candy, one config candy, one ref convention per shape: a
  root-level standalone candy is referenced by the repo path, a sibling candy by
  its named path. No second mechanism.
- **R4/R5** — every reference to the moved candy's path is swept in this cutover
  (`grep -rn candy/crabbox-containerd-config` reads 0); local names, the `require:`
  edge and the skill owner follow the rename.
- **R7** — the fix is proven on the CONSUMER path (plugin-crabbox's validate
  against the branch), not only on the producer's local tree.
- **R10** — the disposable bed runs on this tree.

**RCA — the missed control.** #16's own gate (`box validate` + the R10 bed) passed
because both compose the candy LOCALLY BY NAME; neither exercises the REMOTE ref
that every consumer uses. The structural trigger (`candy/` flips the remote scan
mode) was invisible to a local-only gate. The root fix is the control this PR
adds: a ref-shaped change is proven from a CONSUMER project against the actual
ref, not from the producing repo's local composition. That consumer test is the
`plugin-crabbox box validate` result above.
