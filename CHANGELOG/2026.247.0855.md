# 2026.247.0855 — feat: layer-crabbox — Crabbox CLI candy + skill

## Summary

New standalone layer repo `opencharly/layer-crabbox` — the pinned **Crabbox CLI**
candy (`crabbox:` entity) plus the `crabbox` tool skill (`crabbox-skill:`
entity), mirroring the layer-cue binary-download pattern and the pod-openclaw
root-entity repo shape. Step 1 of the 100%-local Crabbox×OpenCharly integration
(plan/crabbox-integration.md): CLI candy now, coordinator (pod-crabbox) +
check verb (plugin-crabbox) + beds follow.

- Installs the single static `crabbox` binary from the pinned GoReleaser
  release archive: `crabbox_${CRABBOX_VERSION}_linux_${ARCH}.tar.gz` @ tag
  `v${CRABBOX_VERSION}` (asset name `v`-less, tag `v`-prefixed — probe-verified).
  Pin **0.48.1** — probe finding: upstream tag `v0.49.0` exists but ships NO
  release assets; 0.48.1 is the newest asset-backed release.
- Composes the CLI's laptop prerequisites instead of re-shipping them (R3):
  `layer-gh` (git) + `layer-ssh-client` (ssh/ssh-keygen), plus `rsync`/`curl`.
- Declares the `crabbox` alias (wrapper runs in-box via `charly alias`).
- Candy plan checks: binary at `/usr/local/bin/crabbox`; `--version` matches the
  pinned 0.48.1; credential-free `crabbox providers` matrix;
  broker-less `crabbox doctor` (build-time context has no broker — the
  doctor-with-unreachable-broker exit-1 case is handled at the bed layer).
- CI trio: candy gate (`charly box validate` at the pinned charly
  v2026.247.0327) + org-wide pr-validator + tag-on-merge.

### Warnings RCA (R1/B5)

The check-run gate reported exactly one warning, named verbatim from the
`image-build` stage log:

```
warning: podman store is bloated (50.5GiB reclaimable, ~66% of 76.1GiB) — the
overlay-store corruption class tracked in opencharly/charly#173 tracks this
factor. Run `charly clean --deep` (pair with --invalidate for the fullest
reclaim) before building.
```

- **RCA:** operator-HOST storage state on the machine running the bed (a store
  accumulated across many bed runs), NOT a defect in layer-crabbox: the candy's
  build completed and produced a valid image (committed, tagged,
  deployed, started, and re-verified after `update`). No repo-side fix exists or
  applies — the remediation is host hygiene (`charly clean --deep`), recorded
  here as the operator action.
- **Allowlist proof (sanctioned mechanism, not suppression):** the stage line
  reports `warnings=1 allowlisted=10` and the runner's summary.yml diagnostics
  record `errors: 0, warnings: 1, allowlisted: 10` for image-build. The warning
  text is surfaced verbatim in the stage log (never hidden) and counted; the
  runner's allowlist classification is what keeps a known-benign host condition
  from failing the zero-warning gate — every stage still exited PASS (steps=13).
  The remaining `allowlisted` entries are the routine pacman sync notices in the
  same log (`up to date -- skipping`, `local is newer than repo`), likewise
  classified, not suppressed.
