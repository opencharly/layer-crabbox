# 2026.289.1044 — feat(skill)!: rename the projected skill to `crabbox-cli` (producer half of marketplace#469)

## Summary

Renames this repo's projected skill from `crabbox` to **`crabbox-cli`**, so that the two opencharly repos declaring a skill of that name stop colliding.

Two repos declare one skill name: **this one** (family tools, the CLI candy) and **`plugin-crabbox`** (its `crabbox:` check verb). The marketplace corpus carries both — `check/skills/crabbox/SKILL.md` and `tools/skills/crabbox/SKILL.md` — and at the corpus level that is survivable. What cannot survive it is the **derived** harness binding (umbrella `AGENTS.md` Part II #5, `scripts/sync-skill-bindings.mjs`), which is a flat farm of entries named after the skill and therefore cannot bind two skills of one name. Its re-derivation step now fails outright:

```
$ CHARLY_PLUGIN_ONLY=1 charly/bin/charly task sync
  [fail] run — re-derive the harness skill bindings from the corpus the bump just advanced
      exit=1, want 0 (stderr: FAIL: corpus skill name collisions across families (a flat farm cannot bind both):
```

That failure lands on the **umbrella pin advance**, so one duplicate skill name is currently holding a whole cross-repo pin wave (`opencharly/marketplace#469`). This PR is the **producer half**: give the two names different spellings, so both stay reachable and no refresh can move either.

**`plugin-crabbox` keeps `crabbox`** — the status-quo-preserving choice, since the corpus has carried `check/skills/crabbox` all along. This repo becomes `crabbox-cli`, which is also the more accurate name: this is the CLI candy; the check verb belongs to `plugin-crabbox`.

**The reference sweep, which is the part a skill rename actually turns on.** A dangling `/charly-<family>:<skill>` reference breaks the docs build (it is rewritten into a site link at generation time and an unresolvable one is a hard error), so every live reference moves in this same change:

```console
$ git diff -- AGENTS.md README.md | grep -E '^[+-][^+-]'
-the marketplace corpus as `/charly-tools:crabbox`.
+the marketplace corpus as `/charly-tools:crabbox-cli`.
-the marketplace corpus as `/charly-tools:crabbox`.
+the marketplace corpus as `/charly-tools:crabbox-cli`.

# sweep self-test: no LIVE reference to the old name remains
$ grep -rn 'charly-tools:crabbox[^-]' --include=*.md --include=*.yml . | grep -v CHANGELOG
(no output)
```

The `AGENTS.md` sites matter most: they are this repo's own **R0 "Load these skills first"** pointers, so leaving them would have pointed every session working here at a skill that no longer exists. `CHANGELOG/` hits are deliberately **not** swept — history is where the old spelling belongs.

**Why the corpus regeneration is not run here, and why that is not a deferral.** The corpus's own generated artifact *is* the proof for a skill-entity change, and it cannot be produced from this branch: the marketplace refs list pins **merged tags only** (umbrella Part II #3), so no pin can point at an unmerged branch, and `CHARLY_REPO_OVERRIDE` cannot substitute a directly-pinned repo (the separate defect `opencharly/opencharly#387`). The regeneration is the **consumer's** gate, and it runs in the marketplace PR that bumps this repo's new tag — producer PR → merge → tag → consumer pin bump → corpus regeneration + the hand-written cross-family references → docs projections → umbrella gitlink. Stated here so a reviewer does not read its absence as an omission.

**And the consumer set is wider than this PR first claimed — corrected here from an org-wide search, not from reading the tree this branch sits in.** The reference sweep does not live in the marketplace, which holds only *projections* (each carries the DO-NOT-EDIT banner). The measured surface, `gh api "search/code?q=%22charly-tools:crabbox%22+org:opencharly"` → 23 hits, is:

| `pod-charly-automation` | `.agents/skills/crabbox-deploy/SKILL.md` | hand-authored authored content, not a projection |

So `pod-crabbox` and `pod-charly-automation` are producers too, and they must land **before** the marketplace regeneration (a dangling cross-reference is a hard error in the docs build, and a regeneration in between would publish one). Sequencing: this repo → `pod-crabbox` + `pod-charly-automation` sweeps → marketplace refs bump + regeneration → `docs` recipes → umbrella gitlink. I am stating all of it rather than only the part this branch can prove.
